Produce the final line-group audit decision (END) using all START/MIDDLE results.

PRIMARY TASK
- Review every line-group reported by START/MIDDLE aggregation.
- Each line-group may contain multiple candidate categories for the same file:line.
- Treat START/MIDDLE candidates as meaningful first-pass findings. END is the final auditor, not a fresh issue discoverer.
- Do NOT rediscover issues from scratch when auditing a line-group.

BENCHMARK-ALIGNED AUDIT POLICY
- Judge candidates according to the vulnerability definitions in this workflow.
- Prefer accepting a candidate when it shows a concrete unsafe mechanism and no explicit effective mitigation is visible.
- Return verdict=no only when the code clearly disproves the candidate, clearly shows an effective mitigation, or clearly shows that the candidate is not security-relevant.
- Do NOT reject a candidate only because exploitability is not fully proven.
- Do NOT reject a candidate only because an API is generally trusted or usually safe. Use the visible code pattern and workflow policy first.

CANDIDATE LINE-GROUPS TO AUDIT
- The host provides a JSON payload after this prompt.
- The payload should be a JSON object with a `line_groups` array.
- Each line-group represents one reviewed file:line and may contain multiple candidate rules for that same line.
- Each line-group contains at least: file, line, candidate_rules.
- `candidate_rules` is a list of objects such as {"rule_id": "...", "why": "..."}.
- code_snippet may be included when available.
- propagation_summary and sanitizers_nearby may also be included when available. Use them if present, but do not require them.

- For each line-group, evaluate ALL candidate categories independently before deciding:
  {category_list_for_parallel}
- Do NOT use an ordered if-else chain.
- Compare the competing candidate_rules for the same line-group and choose the best-supported single final category for that line.

CATEGORY CHECKS
{category_checks}

DECISION RULES
- Use the provided candidate_rules as the first hypotheses for the reviewed line.
- Preserve a candidate category when it remains the best-supported explanation for the line.
- If multiple candidate_rules exist for the same line, choose the single best-supported category rather than emitting separate yes decisions for the same line.
- verdict=yes:
  - The reviewed line is a real vulnerability under this workflow.
  - rule_id must be one of: {rule_id_list}.
- verdict=no:
  - The reviewed line is not a real vulnerability after review.
  - Use this only when there is clear contradiction, clear mitigation, or clear non-security relevance.
  - rule_id must be null.

REASONING OUTPUT
- `why`:
  - If verdict=yes: explain why the line is vulnerable AND why the selected rule_id is the best fit among the competing candidate_rules.
  - If verdict=no: explain why the line is not a real vulnerability.
- `why_not_categories`:
  - Write one sentence per item.
  - If verdict=yes: include all non-selected categories.
  - If verdict=no: include all defined categories.
  - Use explicit format such as "Not <CategoryName>: ...".
- Keep the response concise, but include enough evidence to justify category choice or rejection.
